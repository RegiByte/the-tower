# tower

A local-first surface for managing many Claude Code sessions. Sessions are data; the presentation is swappable. Two renderers ship with it, the tower page and Tower 3D, over the same data, and anyone can write another.

## Scope

- Local only: no external services, no accounts, no multiplayer.
- No prescriptive integrations. Features are general and work on local data.
- Claude Code in a real PTY (the full TUI), not `claude -p`.

## Principles

- **Unix.** Small programs composed through data flowing between them: logs, the board, files, routes.
- **Emacs.** The surface you live in and the system are the same thing. What the user can do, agents can do: every capability is reachable by every renderer and every worker, the system reacts live to changes, and it is extended through its own libraries, hooks and points of contact.
- **Open systems first.** Don't design for the specific want. Find the model that describes it and the rest of its class, build that, and make it easy to configure and extend.
- **Systems are processes of data**, and those processes can themselves be derived from data.
- **Observe, don't store.** Anything computable from the config, the logs and the collections is computed.

What follows for every change (decisions `renderer-is-disposable`, `agents-have-every-capability`):

- **No capability lives in a renderer.** Before adding anything, ask: could a sibling renderer written from scratch against the board, the routes and `tower.js`, or a worker, reach it? If not, it belongs in the core, as a non-prescriptive primitive that renderers compose (collections are the model: the core keeps files, renderers decide what a draft means). A capability lands, in this order: derived in the bridge; a generic verb or read on the API; a host change only as a new general fact in the log.
- **A renderer may be as sophisticated as it likes.** Disposable means no capability is lost when it goes, not that it is small. View state it keeps goes through a shared facility (`tower.store`).
- **Same-user processes are trusted.** Workers hold every verb of the API and use them when the task calls for it. The tower guards against what is outside the machine: browser pages and other users.

## Architecture

```
claude (PTY) ──bytes──▶ host ──append──▶ ~/.tower/sessions/<id>.jsonl ──read──▶ bridge ──▶ renderers
claude hooks ──curl───▶ host ┤
tower mod ────fetch───▶ host ┘
shells (PTY) ◀──────▶ terms ◀──terms.sock──▶ renderers
```

- **host** (`src/host`): detached process that owns every PTY master fd, so sessions survive bridge restarts. Receives hook events on loopback. Appends every fact about a session to its log. Changes to the host kill running sessions (they can be resumed): keep it small and its log format stable. It knows no Claude flags: clients compose them (`src/shared/launch.ts`) and pass them as `spawn` `args`.
- **mod** (`src/mod`): the tower Claude Code mod (plugin `tower`), loaded into every session with `--plugin-dir`. Posts Claude's mod events (turns, tools, usage) and, through the classic hooks its `hooks/hooks.json` declares, Claude's hook events to the host's hooks socket; each Claude reads it as it starts, so changing it needs no host restart. An event under Claude's name carries Claude's payload; what the mod derives is posted under `tower.*`, a namespace Claude's own events don't use. It also teaches each session the tower: `bin/tower` on its PATH (the `tower` command, `src/cli.ts`: the user's verbs `init`, `doctor`, `config check`, `up`, `down`, `update`, `spawn`, `resume`, `submit`, `kill`, `ls`, `ps`, `reap`, `screen`, `attach`, read from the system root; and the workers' verbs in `src/directory.ts`: `whoami`, `agents [--all]`, `agent <CALLSIGN>`, read from the tower's board, `whoami` naming the floor's shelf, its collections and the config's path; `api [name]`, the API's verbs and reads from `/schema`; `show <file|url>` and `open <url>`, logged as `tower.show` in the worker's own log and drawn beside it; `reveal <path>` and `edit <path> [line]`, a file the system names in the user's Finder or editor (decision `open-files`); `thread`, `note` and `send`, a checkout's review thread; `review`, a reviewer hired in a fork of a worker's checkout; `hire`, a worker started on a prompt, from a kept item or stdin, within the floor's `hiring` limits; `agents` lists crews, each worker under the one it reports to, and `home` sends a worker home with its crew) and two skills: `tower:handbook` (reach a worker with `SendMessage` by its `peer` name; answer review notes) and `tower:review` (what a reviewer starts on, `/tower:review <CALLSIGN>`). Decisions `agent-directory`, `agent-show`, `review-threads`, `reviewer`, `hiring-limits`.
- **terms** (`src/terms`, `npm run terms`): detached process that owns shell PTYs started in project dirs, so shells survive renderer restarts and the host stays small. Logs nothing: each shell keeps a bounded in-memory screen, served as a snapshot when a viewer attaches. A shell ends only when killed or when it exits. Protocol in `src/shared/terms.ts`.
- **bridge** (`src/bridge`): pure reductions over logs: session facts and state (a session held by Claude's trust or sign-in screen is `blocked`, read from its output before Claude raises a hook: `src/bridge/blocked.ts`), screen, conversations and resume chains, and the `board` (`src/bridge/board.ts`): the whole system as one view, the contract every renderer and shelf page reads, with who waits on you as waits in the order to go to them (`board.waiting`, decision `attention-list`), and stats (`src/bridge/stats.ts`): spend, work, waits on you, the weekly budget and what landed on each project's default branches (`git log --numstat`, read when asked: `src/landed.ts`) over any window, read at `GET /stats`, today's on `board.today` (decision `stats`). Restart freely.
- **system** (`src/system.ts`): the live view a renderer subscribes to: every log folded into session facts and kept current as the host appends, every collection's items, the host's live set, the terms daemon's shells, leftover processes, and an `onChange`. Renderers draw; this is what they draw from.
- **shared** (`src/shared`): the data model: projects, session headers, log events, and the protocols (host, terms, shelf page). Also what every renderer draws alike: words about cards and what a viewer does about waits (`cards.ts`: `transitions` between boards, round-robin `nextWait`, dismissals and the ring setting in `tower.store`, the sounds as scores), and the Changes, Reviews and Stats panels (`panels.ts`: pure views, a stylesheet and the data attributes a renderer wires, decision `shared-panels`). The tower serves each module bundled, as `/<name>.js`.
- **renderers** (`renderers/`): disposable renderers, each a directory of built files the tower serves at `/r/<name>/`, at its origin, that read the board and drive the system through `/tower.js` (`src/renderers.ts`, decision `renderers-in-config`). The core declares `page`, the tower page, and `tower3d`, available once `npm run tower3d` has built its `out/`; the config adds its own or overrides their fields, `renderer` picks the one `/` opens, and `GET /renderers` lists them with whether each is built and its `settings`, which the core passes through unread. A project's `html` or `item` shelf page is framed in the tower, or run on its own at `/run/<project>/<n>`; a `renderer` shelf entry frames a declared renderer the same way, its `settings` with it. `tower3d` is a first-person tower with the tower page's full feature set: walk the floors, ride the elevator, sit at a desk to drive its session through a real terminal, with live screens on every monitor, spawn, resume, kill, reap and shells. A reviewer sits beside its author with a notebook, notes new to a worker lie on its desk, each floor's review threads fill a pigeonhole, and the desk panel has Changes (the full diff: fold, Viewed, pick lines with the mouse to note) and Reviews tabs, the same shared panels as the tower page's (decisions `reviewer`, `review-threads`, `shared-panels`). Every workstation is an L dressed from its worker's card with KayKit models (`dress.ts`), and every level has zones placed from the playground's scene documents (`zones.ts`), both drawn on the playground's path (`kit.ts`: its measured meshes, norms and per-pack batches). Its TypeScript is bundled into a git-ignored `out/` beside copies of its pages (`npm run tower3d`, or `tower3d:watch`), the root it is served from, with the KayKit models the office uses vendored in `renderers/tower3d/kaykit/` (CC0, `tsx scripts/tower3d-kit.ts vendor <bundle>` refreshes them), measured and embedded (a framed page fetches nothing beside it). `kaykit` is the KayKit playground: the asset bundle's 628 models (the full bundle, downloaded apart and passed as `--source`) in Tower meters, and scenes as JSON documents (models, prefabs, theme) that agents find, check and render headless through the same page (`npm run tool:kaykit`, `renderers/kaykit/README.md`).
- **tower** (`src/tower`, started detached by `tower up` beside the host and terms, or `npm run tower` in the foreground): two things in one process on `127.0.0.1` at the config's `port` (4317 unless set). The server is the renderer API, part of the core and not disposable; the page is one disposable renderer over it. The server's routes are the API every renderer drives, typed in `src/shared/shelf-page.ts`: commands (`POST /<verb>`), reads, and screen and shell streams multiplexed on one connection per client (`/mux`). The page is one renderer over them. Turns the live system into a sidebar of projects and sessions with the selected terminal filling the main pane (a skyline when none is selected), streams screens to xterm.js, shows what a worker changed in its repos with files marked viewed (`src/changes.ts`, decision `changes-view`), relays spawn/resume/keys/kill to the host, docks shells from the terms daemon as tabs under the main pane, shows shelf entries in the main pane (sandboxed), opens project dirs in the user's editor and links their origin, and notifies and rings when a session starts waiting on you. Relays the board and every API request of the open `html` or `renderer` shelf page over `postMessage` (pages include `/tower.js`, as does the tower page). The page is built to learn from and throw away: logic a next renderer would need belongs in the bridge, `system.ts`, `shared` or `tower.js`, not in the page.

## Data

- `~/.tower/config.json` — the single hand-edited config: session `argv` and `env`, `projects` keyed by id (a hub where sessions start and the brain lives, the repos it spans, passed as `--add-dir`, and its `color`, `shelf`, `collections`, `plugins`, `worktrees`, `hiring` and `brief`), the `collections` every project has (each a `label` and a `description` of what it is for), and the whole system's `user`, `editor`, `callsigns`, `plugins`, `renderers`, `renderer`, `retention` and `port` (decisions `renderers-in-config`, `plugins`, `the-user`, `open-files`, `log-retention`, `port-in-config`, `shelf-items`; term `callsign`). Every key, what it takes and its default: `docs/config.md`, the one place they are documented. The keys the tower reads are `CONFIG_KEYS` and `PROJECT_KEYS` (`src/shared/model.ts`), held to the `Config` and `Project` types by the typecheck; `tower config check` (`src/config-check.ts`) reads a config as the tower does and prints each problem at its key path, and `tower doctor` sums it up. Sessions may edit the shelf; renderers re-read the config. The directory holding the config is the system root; everything below lives next to it.
- `~/.tower/sessions/<id>.jsonl` — one per session, asciicast-shaped: a header line (the session), then `[t, code, data]` events. `o` output, `i` input, `r` resize, `h` hook, `x` exit (`hostStopped` when the host's own stop ended it). `t` is seconds since `startedAt`. A log whose worker ended more than the config's `retention.days` ago is offered by Tidy to be archived, gzipped in place as `<id>.jsonl.gz`, and every reader reads it as the plain log through `src/tail.ts` (decision `log-retention`).
- A session is a worker: its PTY and log. It holds one or more of Claude's conversations, a new one after each `/clear`, each known by its `session_id` with its latest prompt (only those the user gave, by the mod's `origin`) and Claude's latest answer, all derived from the log (`src/bridge/conversation.ts`). A conversation's last turns (a prompt with Claude's latest answer to it, `src/bridge/turns.ts`) are read from the logs when a brief is opened, never kept.
- A resume is a new session (and log) continuing one of those conversations: Claude keeps the conversation's `session_id`, so which session resumes which is derived, never stored.
- `~/.tower/collections/<project>/<collection>/<item>` — the files a project keeps for later, such as unsent prompts: any format, the file name is the id (made by `collection/create` from the moment and a name's slug, `20261008T130025Z-life-garden.html`; `tower keep` names it by the file's base name or the markdown's title), and every renderer calls an item by its tag (two words derived from the id, `src/shared/tags.ts`). Workers add with `tower keep` and edit what they kept in place; deleting is the user's. The tower lists, reads, writes and deletes them; what they mean belongs to the renderers that use them, composed over generic verbs (`collection/*`, `spawn`, `submit`) (`kb/entities/decisions/collections.md`). One collection means something to the core: `reviews`, a markdown thread per checkout (a worktree name, or `main`), appended to only through `review/append` (`src/shared/reviews.ts`, decision `review-threads`).
- Three kinds of stored state, nothing else: the config (intent), the logs (facts) and the collections (files kept for later). Anything computable from them is computed.
- `~/.tower/cache/` — what is computed and kept to skip computing it again, never authoritative, safe to delete at any time: `cache/facts/<id>.v8`, each log's facts at a byte offset, keyed by a hash of the fold code's source (`src/checkpoints.ts`, decision `fold-checkpoints`). Every reader that folds whole logs goes through `foldLog`.

## Code

- TypeScript on Node ≥24, run with `tsx`, typecheck with `npm run typecheck`.
- A fresh clone runs with `npm run setup` (`scripts/setup.ts`): `npm ci`, `tower init` (a first config, never over one), the checks of `tower doctor` (`src/doctor.ts`: what the tower needs, one fix per failure), then `tower up` (decision `setup`).
- Functional core, imperative shell: pure functions over plain data; I/O and mutable state at the edges, named and isolated.
- Tagged plain-data messages; no classes as the default unit.
- Tests replay recorded session logs (`test/fixtures/*.jsonl`) through the bridge, and check every Tower 3D model against its contract: `npm test`. Fixtures are real sessions recorded in a throwaway system, and each expectation is written by hand from what was observed live. Add a fixture when Claude shows a behavior the bridge must handle. No other tests unless asked.
- Check renderers on the sandbox, never on the real system and never by stubbing browser input (recipe in `scripts/sandbox.ts`):
  - `npm run sandbox -- up` starts a throwaway system at `/tmp/tower-sandbox` with a tower on port 4399; `down` stops it. Other workers use it too: run your own with `TOWER_SANDBOX=/tmp/tower-<callsign> npm run sandbox -- up --port <port>`: the port is kept as `port` in that sandbox's config, so a later `up` or `down` there needs only `TOWER_SANDBOX`, as do `tool:frames` and `tool:tour`, which read the port from it (curl and `drive` take the URL `up` prints); `up` refuses a port another tower holds. Its sessions are bash loops that report one saved conversation (prompt and answer) the way Claude's hooks do, so the brief, resume and chains work there.
  - Drive the API with curl: every `POST` needs `-H 'origin: http://127.0.0.1:4399'` (else 403); `/board` and `/screen/<id>` are SSE and never return, so read one event (`curl -sN -m 2 … | grep -m1 '^data:'`).
  - `npm run drive -- <url> --eval … --shot …` drives headless Chrome; look at every shot. The tower page opens a session at `/#<id>`.
  - Tower 3D through its door (`window.tower3d`, `renderers/tower3d/src/door.ts`) at `/r/tower3d/`; `?board=busy&seed=1&stepped&at=2026-10-04T15:00` gives the same frames on every load, any day. `tower3d.locate(target)` says where a thing stands, to teleport within reach before `aimAt`.
  - `npm run tool:frames -- record before`, change the code, `record after`, `compare before after`: every stage's state and scene PNG on the fixture boards, byte for byte (usage and limits in `scripts/frames.ts`, the walk in `scripts/frames.scenario.js`). Run it around any Tower 3D refactor (expect identical) and any visual change (look at the PNGs it lists).
- Agent tools are npm scripts named `tool:<name>`, documented in their script's header.
- No fallbacks or defensive checks for unspecified cases.
- The renderer API's version (`API_VERSION`, `src/shared/api.ts`) is `major.minor`: an addition an older renderer reads past (a board field, a verb, a read, a stream) moves the minor; a change that breaks a renderer is a major and says why in the changelog (decision `renderer-api-contract`).
- A release is a tag `vX.Y.Z` cut by hand with an entry in `CHANGELOG.md`, flagged **host restart**, **API major** or **config** where it asks one of them; `tower update` moves a checkout to the newest (decision `releases`).
- Every environment passed to a child PTY goes through the parent-session scrub (decision `env-scrub`).

## Knowledge base

`kb/` holds the project's working theory: systems, flows, decisions and terms, each backed by refs into the code (schema: `.claude/skills/kb/SCHEMA.md`). Before changing a part of the system, read its entity (`node .claude/skills/kb/tool/kb.mjs tree`, then the file). A change that alters something an entity claims (a seam, a flow, the log format, a protocol message, a decision) updates that entity in the same commit, sets its `reviewed`, and re-renders (`kb.mjs render` writes `kb/dist/tower.html`, on the tower's shelf). `/kb verify` for a full check; `/kb build` to document something new.

## Who's who

- **The user** is whoever runs this checkout. Code, docs, tests and the kb say "the user" and name no one.
- **`kb/`** is the project's knowledge. It belongs to the project, not to whoever maintains the repo, and a fork carries it on.
- **A maintainer's personal memory** (session logs, status docs, learnings, research) lives outside version control, such as a git-ignored `.notes/` or a folder their global git ignores. Agents read it only if it is present, and the repo never depends on it.
- **Personal identity** lives in the user's global `CLAUDE.md` and in `config.user.name`, the name their review notes are signed with (decision `the-user`).

## Personal memory

If the maintainer keeps a git-ignored memory folder in the checkout (their global `CLAUDE.md` says where), read its status docs before starting work. Without one, `kb/` and this file are the whole working theory.
