# tower

A local-first surface for managing many Claude Code sessions. Sessions are data; the presentation is swappable. Three renderers ship with it, the tower page, Tower 3D and The Week, over the same data, and anyone can write another.

## Scope

- Local only: no external services, no accounts, no multiplayer.
- No prescriptive integrations. Features are general and work on local data.
- Claude Code in a real PTY (the full TUI), not `claude -p`.

## Principles

- **Unix.** Small programs composed through data flowing between them: logs, the board, files, routes.
- **Emacs.** The surface you live in and the system are the same thing. What the user can do, agents can do: every capability is reachable by every renderer and every worker, the system reacts live to changes, and it is extended through its own libraries, hooks and points of contact.
- **Open systems first.** Don't design for the specific want. Find the model that describes it and the rest of its class, build that, and make it easy to configure and extend.
- **Systems are processes of data**, and those processes can themselves be derived from data.
- **Observe, don't store.** Anything computable from the config, the logs and the collections is computed.

What follows for every change (decisions `renderer-is-disposable`, `agents-have-every-capability`):

- **No capability lives in a renderer.** Before adding anything, ask: could a sibling renderer written from scratch against the board, the routes and `tower.js`, or a worker, reach it? If not, it belongs in the core, as a non-prescriptive primitive that renderers compose (collections are the model: the core keeps files, renderers decide what a draft means). A capability lands, in this order: derived in the bridge; a generic verb or read on the API; a host change only as a new general fact in the log.
- **A renderer may be as sophisticated as it likes.** Disposable means no capability is lost when it goes, not that it is small. View state it keeps goes through a shared facility (`tower.store`).
- **Same-user processes are trusted.** Workers hold every verb of the API and use them when the task calls for it. The tower guards against browser pages; the machine's other accounts and its network are the machine's to guard.

## Architecture

```
claude (PTY) ──bytes──▶ host ──append──▶ ~/.tower/sessions/<id>.jsonl ──read──▶ bridge ──▶ renderers
claude hooks ──curl───▶ host ┤
tower mod ────fetch───▶ host ┘
shells (PTY) ◀──────▶ terms ◀──terms.sock──▶ renderers
```

- **host** (`src/host`): detached process that owns every PTY master fd, so sessions survive bridge restarts. Receives hook events on loopback. Appends every fact about a session to its log: the `tower.*` facts its `spawn` carries right after the header, and a `tower.*` fact about one an earlier host ran too (`fact`, decision `let-go`). Changes to the host kill running sessions (they can be resumed): keep it small and its log format stable. It knows no Claude flags: clients compose them (`src/shared/launch.ts`) and pass them as `spawn` `args`.
- **mod** (`src/mod`): the tower Claude Code mod (plugin `tower`), loaded into every session with `--plugin-dir`. Posts Claude's mod events (turns, tools, usage) and, through the classic hooks its `hooks/hooks.json` declares, Claude's hook events to the host's hooks socket; each Claude reads it as it starts, so changing it needs no host restart. An event under Claude's name carries Claude's payload; what the mod derives is posted under `tower.*`, a namespace Claude's own events don't use. It also teaches each session the tower: `bin/tower` on its PATH (the `tower` command, `src/cli.ts`: the user's verbs `init`, `doctor`, `config check`, `up`, `down`, `update`, `spawn`, `resume`, `submit`, `kill`, `live`, `ls`, `ps`, `reap`, `screen`, `attach`, read from the system root, and `app`, the tower as a Mac app built from the checkout (`src/app.ts`, `apps/macos`, decision `macos-app`); and the workers' verbs in `src/directory.ts`: `whoami`, `agents [--all]`, `agent <CALLSIGN>`, read from the tower's board, `whoami` naming the floor's shelf, its collections and the config's path; `api [name]`, the API's verbs and reads from `/schema`; `flows [verb]`, where extensions take part in each core verb, its stages open, wrapped or sealed (`src/shared/flows.ts`, served in `/schema`); `probes [run quota]`, the quota extension's probe and where it stands, `run` reading now; `extensions [restart|check|freeze]`, each extension the tower found, its state, slots and problems, `restart` one read and imported again, `check` a folder read, resolved and started in a throwaway process, `freeze` its `contract.json` written (`src/extension-check.ts`); `x [<cap> <verb> [input]]`, an extension's verb called, or every running one's verbs listed (every other word after `tower` stays the core's); `keep` and `kept` (the floor's collections: an item kept for later, the items kept); `policies [approve|run]` and `runs` (the floor's policies, where each stands, and a policy's latest runs; `whoami` tells a run what it is) and `read <tag|id>` (an item's contents); `show <file|url>` and `open <url>`, logged as `tower.show` in the worker's own log and drawn beside it; `reveal <path>` and `edit <path> [line]`, a file the system names in the user's Finder or editor (decision `open-files`); `thread`, `note` and `send`, a checkout's review thread; `review`, a reviewer hired in a fork of a worker's checkout; `hire`, a worker started on a prompt, from a kept item or stdin, within the floor's `hiring` limits; `agents` lists crews, each worker under the one it reports to, `home` sends a worker home with its crew, and `let-go` takes a worker stranded by the host off duty, still resumable) and three skills: `tower:handbook` (reach a worker with `SendMessage` by its `peer` name; answer review notes), `tower:review` (what a reviewer starts on, `/tower:review <CALLSIGN>`) and `tower:guide` (teaching the user the tower on their own floors, from `docs/usage.md`). Decisions `agent-directory`, `agent-show`, `review-threads`, `reviewer`, `hiring-limits`.
- **terms** (`src/terms`, `npm run terms`): detached process that owns shell PTYs started in project dirs, so shells survive renderer restarts and the host stays small. Logs nothing: each shell keeps a bounded in-memory screen, served as a snapshot when a viewer attaches. A shell ends only when killed or when it exits. Protocol in `src/shared/terms.ts`.
- **bridge** (`src/bridge`): pure reductions over logs: session facts and state (a session held by Claude's trust or sign-in screen is `blocked`, read from its output before Claude raises a hook: `src/bridge/blocked.ts`), screen, conversations and resume chains, and the `board` (`src/bridge/board.ts`): the whole system as one view, the contract every renderer and shelf page reads, with who waits on you as waits in the order to go to them (`board.waiting`, decision `attention-list`), and stats (`src/bridge/stats.ts`): spend, work, waits on you, the weekly budget and what landed on each project's default branches (`git log --numstat`, read when asked: `src/landed.ts`) over any window, read at `GET /stats`, today's on `board.today` (decision `stats`). Restart freely.
- **system** (`src/system.ts`): the live view a renderer subscribes to: every log folded into session facts and kept current as the host appends, every stream an extension folds, every collection's items, the host's live set, the terms daemon's shells, leftover processes, and an `onChange`. Renderers draw; this is what they draw from.
- **shared** (`src/shared`): the data model: projects, session headers, log events, and the protocols (host, terms, shelf page). Also what every renderer draws alike: words about cards and what a viewer does about waits and policies' offers (`cards.ts`, a module per concern beside it, `waits.ts` and `rings.ts` among them, served as one: `transitions` between boards, round-robin `nextWait` over the `attentionOrder`, dismissals and the ring setting in `tower.store`, the sounds as scores, an offer's its own), any collection's items as trays and reads (`items.ts`, decision `collection-trays`), and the Changes, Stats and Policies panels (`panels.ts`: pure views, a stylesheet and the data attributes a renderer wires, the Reviews panel the reviews extension's client, decision `shared-panels`). The tower serves each module bundled, as `/<name>.js`.
- **renderers** (`renderers/`): disposable renderers (how a user extends or copies one, and what the core promises them: `docs/extending.md`), each a directory of built files the tower serves at `/r/<name>/`, at its origin, that read the board and drive the system through `/tower.js` (`src/renderers.ts`, decision `renderers-in-config`). The core declares `page`, the tower page, `week`, The Week (a plain page reading the budget week as a yearbook: its totals, every worker by floor, the hours' rhythm, superlatives and a quote, all read from the board, `/stats` and the archives), and `tower3d`, available once `npm run tower3d` has built its `out/`; the config adds its own or overrides their fields, `renderer` picks the one `/` opens, and `GET /renderers` lists them with whether each is built and its `settings`, which the core passes through unread. A project's `html` or `item` shelf page is framed in the tower, or run on its own at `/run/<project>/<n>`; a `renderer` shelf entry frames a declared renderer the same way, its `settings` with it. `tower3d` is a first-person tower with the tower page's full feature set: walk the floors, ride the elevator, sit at a desk to drive its session through a real terminal, with live screens on every monitor, spawn, resume, kill, reap and shells. A reviewer sits beside its author with a notebook, notes new to a worker lie on its desk, each floor's review threads fill a pigeonhole, and the desk panel has Changes (the full diff: fold, Viewed, pick lines with the mouse to note) and Reviews tabs, the same shared panels as the tower page's (decisions `reviewer`, `review-threads`, `shared-panels`). Every workstation is an L dressed from its worker's card with KayKit models (`dress.ts`), and every level has zones placed from the playground's scene documents (`zones.ts`), both drawn on the playground's path (`kit.ts`: its measured meshes, norms and per-pack batches). The city, the building's shell and its roof plant are geometry generated at load (`exterior/`); the lighting (a sun that follows the clock with its shadows, contact shadows and the night's bloom, `light/`) is a setting in its popover, on by default, applied on reload (decision `tower3d-look`). It starts under a loading screen, the elevator's panel lighting a button per stage, and draws nothing until its first board is built and its shaders compiled off the main thread (decision `tower3d-start`). Its TypeScript is bundled into a git-ignored `out/` beside copies of its pages (`npm run tower3d`, or `tower3d:watch`), the root it is served from, with the KayKit models the office uses vendored in `renderers/tower3d/kaykit/` (CC0, `tsx scripts/tower3d-kit.ts vendor <bundle>` refreshes them), the forge's real-size props (a kit of props made for the tower in a repository of its own, CC0) vendored whole from its `dist/` in `renderers/tower3d/forge/` and measured as one more pack, bound by material name (`tsx scripts/tower3d-kit.ts vendor-forge <dist>`, decision `forge-kit`), and its workers KayKit characters on one rig posed by KayKit's clips on the sim clock, packed into `kaykit/Characters/` (`tsx scripts/tower3d-characters.ts`, decision `kaykit-workers`), with parts modelled by hand in a Blender kit beside them, `parts/parts.blend`, each joining a look's slot by its name (`npm run tower3d:parts` exports them to `parts/parts.glb`, `renderers/tower3d/parts/README.md`), measured and built as files into `out/assets/`, which each page fetches as it starts (a renderer's files are served with CORS, so it fetches them framed too; an `html` shelf page's are not, and it fetches nothing beside it: decision `bundled-renderer`). `kaykit` is the KayKit playground: the asset bundle's 628 models (the full bundle, downloaded apart and passed as `--source`) in Tower meters, and scenes as JSON documents (models, prefabs, theme) that agents find, check and render headless through the same page (`npm run tool:kaykit`, `renderers/kaykit/README.md`).
- **extensions** (`src/shared/extensions.ts`, `src/bridge/extensions.ts`, `src/extensions.ts`, `src/tower/extensions.ts`): folders holding an `extension.json` manifest and optionally a server module whose default export is `start(ctx)`, bundled in the checkout's `extensions/<id>/` (`drafts`: its collection, and its client, the drafts editor renderers import at `/x/drafts/drafts.js`; `quota`, the quota probe; `policies`, standing work started at its slots; `reviews`, the review threads and their Reviews panel at `/x/reviews/`; `autotidy`, what a worker leaves tidied once it goes home, as its settings say) or added by the config's `extensions`; `examples/extensions/` holds ones to copy (`narrate`), each loaded by `npm test`. Each provides one capability, the core being `tower` at `API_VERSION`. Every manifest is read strictly and resolved before any code runs (refused, with problems, when it can't load), the rest started as braided resources `x:<cap>` beside the tower's own and reconciled when the config changes; `board.extensions`, `GET /extensions`, `tower extensions` and `tower doctor` show each one's state and problems, and doctor runs the checks they declare (decision `extensions`). Their verbs and reads go through the one dispatch (`POST`/`GET /<cap>/…`, `tower x`), their stores are collections, streams and session facts, and their folds put each one's part and contributions on the board after the core's is built (`src/bridge/folds.ts`: `x` on a subject, `board.adds`, `board.asks`), drawn by every renderer through `/cards.js`, their client commands served at `/x/<cap>/`, their slots fired by the tower's slot loop and their board triggers called on each board that changes (`src/tower/triggers.ts`); the built-ins' old names keep answering through `LEGACY` until 2.0 (verbs and reads dispatched to their new names, deprecated; old board fields copied from their parts; served modules at their old URLs; stream folders kept: `src/bridge/legacy.ts`); `extension/restart` imports an extension's folder afresh through a resolve hook (`src/fresh-imports.ts`); every call runs through the chain of `around` links wrapping its verb, and hooks are answered through `answers` (`src/tower/chains.ts`); their launch contributors shape every spawn, resume and fork on their floors (spawn fields logged as facts before the PTY starts, parts the runtime places, `tower.exempt` and `tower.reports-to` as core facts: `src/bridge/launch.ts`).
- **tower** (`src/tower`, started detached by `tower up` beside the host and terms, or `npm run tower` in the foreground): two things in one process on `127.0.0.1` at the config's `port` (4317 unless set). The server is the renderer API, part of the core and not disposable; the page is one disposable renderer over it. The server's routes are the API every renderer drives, typed in `src/shared/shelf-page.ts`: commands (`POST /<verb>`), reads, and screen and shell streams multiplexed on one connection per client (`/mux`). The page is one renderer over them. Turns the live system into a sidebar of projects and sessions with the selected terminal filling the main pane (a skyline when none is selected), streams screens to xterm.js, shows what a worker changed in its repos with files marked viewed (`src/changes.ts`, decision `changes-view`), relays spawn/resume/keys/kill to the host, docks shells from the terms daemon as tabs under the main pane, shows shelf entries in the main pane (sandboxed), opens project dirs in the user's editor and links their origin, and notifies and rings when a session starts waiting on you. Runs the slot loop beside them (`src/slots.ts`), whose source is the extensions' manifest slots and the slots their floor and board folds give (`src/shared/slots.ts`, rules of crons or `every`): the policies extension's runner among them (decision `policies`). Relays the board and every API request of the open `html` or `renderer` shelf page over `postMessage` (pages include `/tower.js`, as does the tower page). The page is built to learn from and throw away: logic a next renderer would need belongs in the bridge, `system.ts`, `shared` or `tower.js`, not in the page.

## Data

- `~/.tower/config.json` — the single hand-edited config: session `argv` and `env`, `projects` keyed by id (a hub where sessions start and the brain lives, the repos it spans, granted as file access only through `permissions.additionalDirectories` (decision `repos-file-access-only`), and its `color`, `shelf`, `collections`, `plugins`, `worktrees`, `hiring`, `brief`, `extensions` (settings by id) and `capabilities` (one turned off on that floor)), the `collections` every project has (each a `label` and a `description` of what it is for), and the whole system's `user`, `editor`, `callsigns`, `plugins`, `renderers`, `renderer`, `retention`, `probes` (the quota extension's old spelling, `src/bridge/legacy.ts`), `port`, `keys`, the chords that replace the keymap's defaults, and `extensions`, by id (decisions `extensions`, `renderers-in-config`, `plugins`, `the-user`, `open-files`, `log-retention`, `port-in-config`, `shelf-items`; term `callsign`). Every key, what it takes and its default: `docs/config.md`, the one place they are documented. The keys the tower reads are `CONFIG_KEYS` and `PROJECT_KEYS` (`src/shared/model.ts`), held to the `Config` and `Project` types by the typecheck; `tower config check` (`src/config-check.ts`) reads a config as the tower does and prints each problem at its key path, and `tower doctor` sums it up. Sessions may edit the shelf; renderers re-read the config. The directory holding the config is the system root; everything below lives next to it.
- `~/.tower/sessions/<id>.jsonl` — one per session, asciicast-shaped: a header line (the session, and its `runtime`, absent from the logs of older hosts, which are Claude's), then `[t, code, data]` events. `o` output, `i` input, `r` resize, `h` hook, `x` exit (`signal` when an uncaught signal ended it, `hostStopped` when the host's own stop did). `t` is seconds since `startedAt`. A log whose worker ended more than the config's `retention.days` ago is offered by Tidy to be archived, gzipped in place as `<id>.jsonl.gz`, and every reader reads it as the plain log through `src/tail.ts` (decision `log-retention`).
- A session is a worker: its PTY and log. It holds one or more of Claude's conversations, a new one after each `/clear`, each known by its `session_id` with its latest prompt (only those the user gave, by the mod's `origin`) and Claude's latest answer, all derived from the log (`src/bridge/conversation.ts`). A conversation's last turns (a prompt with Claude's latest answer to it, `src/bridge/turns.ts`) are read from the logs when a brief is opened, never kept.
- A resume is a new session (and log) continuing one of those conversations: Claude keeps the conversation's `session_id`, so which session resumes which is derived, never stored.
- `~/.tower/collections/<project>/<collection>/<item>` — the files a project keeps for later, such as unsent prompts: any format, the file name is the id (made by `collection/create` from the moment and a name's slug, `20261008T130025Z-life-garden.html`; `tower keep` names it by the file's base name or the markdown's title), and every renderer calls an item by its tag (two words derived from the id, `src/shared/tags.ts`). Workers add with `tower keep` and edit what they kept in place; deleting is the user's. The tower lists, reads, writes and deletes them; what they mean belongs to the renderers that use them, composed over generic verbs (`collection/*`, `spawn`, `submit`) (`kb/entities/decisions/collections.md`). Extensions declare collections of their own: `reviews`, the bundled reviews extension's (`extensions/reviews/`), owned, a markdown thread per checkout (a worktree name, or `main`), appended to only through `reviews/append`, its format and Reviews panel its client (`/x/reviews/reviews.js`, `/x/reviews/panel.js`), each card's thread and each floor's threads folded as `x.reviews` from the parsed files and the core's checkout states (`src/bridge/checkouts.ts`), `review/append`, `GET /reviews/<project>`, `/reviews.js` and the old board fields kept by `LEGACY` until 2.0 (decision `review-threads`); `policies`, the bundled policies extension's (`extensions/policies/`), standing work started at its slots, each a `# Title`, a fenced json header (`when` crons, `check`, `start`, `live`, `hire`, `runner`, `x`) and the prose a run's worker starts on, parsed in `extensions/policies/policy-file.ts`, said in words and decided in its client (`/x/policies/policies.js`), fired by the core's slot loop and acted on through `policies/run`, `policies/pass` and `policies/approve` (`policy/*` kept by `LEGACY` until 2.0, decision `policies`).
- `~/.tower/streams/system/<stream>/YYYY-MM.jsonl` — logs of facts the tower observes that belong to no session, one per UTC month, written only by the tower: an extension's system streams, such as the bundled quota extension's reads of the account's rate limits (`extensions/quota`, kept in the folder `streams/system/probe.quota/`), each Claude's `get_usage` answer as it came or why there is none; a fact of kind `tower/rate-limits` is folded beside the sessions' readings into the board's rate limits and the weekly budget (`src/bridge/rate-limits.ts`, decision `probes`). `~/.tower/streams/projects/<project>/<stream>/YYYY-MM.jsonl` — a project's: the policies extension's `runs/` (`r` a policy's run, `s` a slot passed and why) and `approvals/` (`a` a policy's hash approved), its streams `policies.runs` and `policies.approvals` kept in those folders by `LEGACY`, folded into its part of each floor and card (`floor.x.policies`, `card.x.policies.run`, copied to `floor.policies`, `board.offers` and `card.run` until 2.0) and read at `GET /policies/runs/<project>` (decision `policies`). Every stream is read and appended the same way (`src/bridge/streams.ts`, `src/streams.ts`).
- Three kinds of stored state, nothing else: the config (intent), the logs (facts: one writer per log, the host's `sessions/` and the tower's `streams/`) and the collections (files kept for later). Anything computable from them is computed.
- `~/.tower/cache/` — what is computed and kept to skip computing it again, never authoritative, safe to delete at any time: `cache/facts/<id>.v8`, each log's facts at a byte offset, keyed by a hash of the fold code's source (`src/checkpoints.ts`, decision `fold-checkpoints`). Every reader that folds whole logs goes through `foldLog`.

## Code

- TypeScript on Node ≥24, run with `tsx`, typecheck with `npm run typecheck`. The JavaScript served as written (`src/tower/tower.js`, `renderers/week/week.js`, the mod's `register.js`, and the tower page's `renderers/page/page.js` in a project of its own with xterm's globals, `tsconfig.page.json`) is checked by it too, typed through JSDoc from the TypeScript types (`tsconfig.client.json`).
- A fresh clone runs with `npm run setup` (`scripts/setup.ts`): `npm ci`, `tower init` (a first config, never over one), the checks of `tower doctor` (`src/doctor.ts`: what the tower needs, one fix per failure), then `tower up` (decision `setup`).
- Functional core, imperative shell: pure functions over plain data; I/O and mutable state at the edges, named and isolated.
- Tagged plain-data messages; no classes as the default unit.
- State with a lifecycle (more than two states, anything timed, or anything two renderers need) is a machine: pure steps returning the next state and tagged effects, wired one handler per event into `loop` (`src/shared/loop.ts`), timers as effects, I/O in the renderer's executors. One any renderer needs lives in `src/shared`, served; one renderer's own beside it (decision `machines`).
- Tests replay recorded session logs (`test/fixtures/*.jsonl`) through the bridge, check every Tower 3D model against its contract, and boot the tower server on a throwaway root to drive its API over HTTP once (`test/server.test.ts`): `npm test`. Fixtures are real sessions recorded in a throwaway system, and each expectation is written by hand from what was observed live. Add a fixture when Claude shows a behavior the bridge must handle. No other tests unless asked.
- Check renderers on the sandbox, never on the real system and never by stubbing browser input (recipe in `scripts/sandbox.ts`):
  - `npm run sandbox -- up` starts a throwaway system and prints how to reach it; `down` stops it, and no other. Run by a tower worker, it is the worker's own, at `/tmp/tower-<callsign>` on a free port; run by hand, `/tmp/tower-sandbox` on port 4399. `TOWER_SANDBOX` names another root and `--port` another port, kept in its config. Its sessions are bash loops that report one saved conversation (prompt and answer) the way Claude's hooks do, so the brief, resume and chains work there.
  - **`tower` reads the real system unless run through `npm run -s sandbox -- run <command>`**, which points it at the sandbox's config, puts the sandbox's URL in `TOWER_URL` for curl and `drive`, and drops the worker's own session from the environment (several commands: `run sh <<'SH'` … `SH`). `tool:frames` and `tool:tour` find the sandbox on their own. Inside a sandbox, plain `tower agents` refuses (you have no card there): use `tower agents --all`. Stop only what you started: `down`, or a PID you saved; never `pkill`, `killall` or `tower reap`.
  - Drive the API with curl: every `POST` needs `-H "origin: $TOWER_URL"` (else 403); `/board` and `/screen/<id>` are SSE and never return, so read one event (`curl -sN -m 2 … | grep -m1 '^data:'`).
  - `npm run drive -- <url> --eval … --shot …` drives headless Chrome; look at every shot. The tower page opens a session at `/#<id>`.
  - Tower 3D through its door (`window.tower3d`, `renderers/tower3d/src/door.ts`) at `/r/tower3d/`; `?board=busy&seed=1&stepped&at=2026-10-04T15:00` gives the same frames on every load, any day. `tower3d.locate(target)` says where a thing stands, to teleport within reach before `aimAt`.
  - `npm run tool:frames -- record before`, change the code, `record after`, `compare before after`: every stage's state and scene PNG on the fixture boards, byte for byte (usage and limits in `scripts/frames.ts`, the walk in `scripts/frames.scenario.js`). Run it around any Tower 3D refactor (expect identical) and any visual change (look at the PNGs it lists).
- Agent tools are npm scripts named `tool:<name>`, documented in their script's header.
- `npm run tool:contrast` measures every colour pair the renderers draw from the tokens against WCAG AA, in both schemes; run it after any change to `design.ts`'s palettes or a new use of a token as text.
- No fallbacks or defensive checks for unspecified cases.
- The renderer API's version (`API_VERSION`, `src/shared/api.ts`) is `major.minor`: an addition an older renderer reads past (a board field, a verb, a read, a stream) moves the minor; a change that breaks a renderer is a major and says why in the changelog (decision `renderer-api-contract`).
- A release is a tag `vX.Y.Z` cut by hand with an entry in `CHANGELOG.md`, flagged **host restart**, **API major** or **config** where it asks one of them; `tower update` moves a checkout to the newest (decision `releases`).
- Every environment passed to a child PTY goes through the parent-session scrub (decision `env-scrub`).

## Knowledge base

`kb/` holds the project's working theory: systems, flows, decisions and terms, each backed by refs into the code (schema: `.claude/skills/kb/SCHEMA.md`). Before changing a part of the system, read its entity (`node .claude/skills/kb/tool/kb.mjs tree`, then the file). A change that alters something an entity claims (a seam, a flow, the log format, a protocol message, a decision) updates that entity in the same commit, sets its `reviewed`, and re-renders (`kb.mjs render` writes `kb/dist/tower.html`, on the tower's shelf). `/kb verify` for a full check; `/kb build` to document something new.

## Contributing

A pull request is checked by CI (`.github/workflows/ci.yml`); run the same before pushing, and leave the tree as committed:

- `npm run typecheck`, `npm test`, `npm run tower3d`, then `npm run test:tower3d-boot` (the built Tower 3D boots on a fixture board in headless Chrome, clean of page errors: `scripts/tower3d-boot.ts`) and `npm run test:page-boot` (the tower page boots over a tower alone and draws its floor and skyline, clean of page errors: `scripts/page-boot.ts`), and `xcrun swiftc -typecheck -swift-version 5 apps/macos/Sources/*.swift` if `apps/macos` changed. `git status` is clean after them (CI fails on a file they add or rewrite).
- `node .claude/skills/kb/tool/kb.mjs verify`. A change that contradicts a kb entity updates it in the same commit (Knowledge base, above), and a branch lands with no suspect of its own: `kb.mjs verify --since origin/main` lists those its commits caused, each cleared by checking the entity's claims and setting its `reviewed`. CI lists them on a pull request as warnings, and does not fail on them.
- A served module's exports change: `npm run served:update`. A board shape change: `npm run schema:board`. An addition moves `API_VERSION`'s minor, in the PR. A removal or rename is an API major: the PR says what renderers use instead, for the CHANGELOG (decision `renderer-api-contract`).
- `CHANGELOG.md`, tags and releases are the maintainer's: leave them.
- One concern per commit. Check renderers on the sandbox (Code, above); a UI change carries screenshots in the PR body, and says what was and wasn't run (Tower 3D, say).
- A host change kills running sessions when the host restarts: say so in the PR.

Writing a renderer or a config: `docs/extending.md`, `docs/config.md`.

## Who's who

- **The user** is whoever runs this checkout. Code, docs, tests and the kb say "the user" and name no one.
- **`kb/`** is the project's knowledge. It belongs to the project, not to whoever maintains the repo, and a fork carries it on.
- **A maintainer's personal memory** (session logs, status docs, learnings, research) lives outside version control, such as a git-ignored `.notes/` or a folder their global git ignores. Agents read it only if it is present, and the repo never depends on it.
- **Personal identity** lives in the user's global `CLAUDE.md` and in `config.user.name`, the name their review notes are signed with (decision `the-user`).

## Personal memory

If the maintainer keeps a git-ignored memory folder in the checkout (their global `CLAUDE.md` says where), read its status docs before starting work. Without one, `kb/` and this file are the whole working theory.
